## 1. Что заложено в ТЗ (разбор Excel)

Таблица — не форма для заполнения, а **прототип алгоритма планирования**. Из неё восстанавливается доменная модель и расчёт.

### 1.1. Сущности

| Сущность | Поля из ТЗ | Комментарий |
|---|---|---|
| **Заказ (договор / заказчик)** | заказчик, дата договора, дата запуска в производство | Один заказ содержит несколько изделий с разным приоритетом |
| **Изделие** | вид (Кухня, Шкаф, Тумба, Прихожая, Зеркало, Техника…), количество, приоритет (1 — высший), м², м.пог = м² × 10 | Единица планирования — изделие, а не заказ (B14). «Коэф. конструктора» из Excel — не поле изделия, а КПД сотрудника (уточнено 10.09) |
| **Участок (рабочий центр)** | название, единица измерения (изделие / м² / м.пог / заказ), пропускная способность в рабочий день, «рабочие дни для достижения пропускной способности», нормативный вес сотрудников, кол-во сотрудников | Список расширяемый и переупорядочиваемый (B56–B58) |
| **Специалист** | роль (мастер / помощник / снабженец / сборщик / ОТК / конструктор), вес / КПД (1 / 0.8 / 0.6 / 0.3…), привязка к участку | КПД конструктора — свойство человека, не позиции заказа; присутствие меняет мощность участка |
| **Маршрут** | последовательность участков и зависимости «старт после окончания предыдущего», часть участков параллельна | В модели — DAG; в первой версии единый линейный маршрут для всех изделий (уточнение заказчика, §1.4) |
| **Документы изделия** (добавлено 10.09) | два хранилища: производственные (чертежи, схемы, дизайн) и на закупку (материалы, фурнитура, всё что докупается) | Прикладывает конструктор; наличие документов на закупку определяет, идёт ли изделие через Комплектацию |

### 1.2. Участки из примера (порядок и связи по формулам)

```
Конструирование №1 ─┐
Конструирование №2 ─┤
                    ├──► Пила (форматник) ──► Кромкооблицовка ──► Присадка ──► Фрезерование
                    │
                    └──► Комплектация (снабжение) ──► Сборка ──► ОТК ──► [+ новый участок]
```

В формулах `Сборка` стартует после `Комплектации`; в комментарии X28 — после `Присадки` **и** `Комплектации` (то есть `max()` по всем предшественникам). Куда впадает `Фрезерование` — из файла не ясно.

**Уточнено заказчиком 10.09.2026** (ответы 3 и 7): в первой версии все изделия проходят все участки, а движение по станочным этапам начинается только после подтверждения `Комплектации`, что все детали и материалы в наличии. Маршрут по умолчанию становится линейным:

```
Конструирование (№1 | №2) ──► Комплектация [шлюз: «всё в наличии»] ──► Пила ──► Кромкооблицовка ──► Присадка ──► Фрезерование ──► Сборка ──► ОТК
```

**Подтверждено заказчиком 10.09.2026 (второй раунд).** Уточнение: шлюз Комплектации **условный по изделию**. Конструктор, завершая изделие, прикладывает документы в два хранилища — производственные (чертежи, схемы, дизайн) и на закупку (материалы, фурнитура). Если документов на закупку нет — изделие сразу уходит на Пилу; если есть — сначала Комплектация, которая подтверждает наличие **по каждому изделию отдельно**, и изделие уходит в работу, не дожидаясь остальных изделий заказа.

```
                                   ┌── есть документы на закупку ──► Комплектация [«всё в наличии» по изделию] ──┐
Конструирование (заказ целиком) ───┤                                                                              ├──► Пила ──► Кромка ──► Присадка ──► Фрезерование ──► Сборка ──► ОТК
                                   └── документов на закупку нет ─────────────────────────────────────────────────┘
```

Лишние участки для конкретных видов изделий отключаются позже (флаг «участок пропускается» в маршруте вида изделия). Возможность параллельных веток в модели сохраняется (DAG), но в MVP не используется.

### 1.3. Расчёт (восстановлен из формул)

```
коэф_производительности = реальный_вес_присутствующих / нормативный_вес
время_дней             = ROUNDDOWN((выдано_объём / пропускная_способность) / коэф_производительности, 2)
дата_старта            = дата_готовности предыдущего участка   (для конструирования — дата запуска)
дата_готовности        = ROUNDUP(дата_старта + время_дней, 0)
нераспределено         = план_объём_всего − выдано_объём
```

Контрольный пример (используется как golden-test движка):

| Участок | Выдано | Мощность/день | Время, дн | Старт | Готовность |
|---|---|---|---|---|---|
| Конструирование №1 | 2.7 изд. | 0.5 | 5.40 | 02.08 | 08.08 |
| Конструирование №2 | 1 изд. | 0.5 | 2.00 | 02.08 | 04.08 |
| Пила | 200 м² | 100 | 2.00 | 04.08 | 06.08 |
| Кромкооблицовка | 780 м.п. | 500 | 1.56 | 06.08 | 08.08 |
| Присадка | 209 м² | 140 | 1.49 | 08.08 | 10.08 |
| Фрезерование | 25 м² | 30 | 0.83 | 10.08 | 11.08 |
| Комплектация | 5 заказов | 4 | 1.25 | 04.08 | 06.08 |
| Сборка | 179 м² | 80 | 2.23 | 06.08 | 09.08 |
| ОТК | 179 м² | 80 | 2.23 | 09.08 | 12.08 |

Замеченные особенности прототипа, которые в системе надо сделать иначе:

- Дни прибавляются **календарно** (02.08.2026 — воскресенье); заказчик подтвердил: считаем по **рабочим дням 5/2** — нужен производственный календарь с праздниками и переносами.
- `ROUNDUP` на каждом участке накапливает ошибку до +1 дня на шаг; в системе считать в долях дня с переносом остатка, округлять только для отображения.
- Расчёт агрегированный по участку; ТЗ (B14) требует прогон **поштучно** по каждому изделию с накоплением в календарь. Оба представления нужны: загрузка участка по дням + путь каждого изделия.
- «Рабочие дни для достижения пропускной способности» (строка 35) — по разъяснению заказчика это срок выполнения 100 % пропускной способности: конструктор делает 1 изделие за 2 дня (0.5/день). В системе мощность участка задаётся парой **«X единиц за N рабочих дней»**, суточная мощность = X / N вычисляется.

### 1.5. Явные функциональные требования (B56–B61, X40)

1. Добавлять участки.
2. Менять участки местами.
3. Участок может зависеть от пропускной способности предыдущего или работать параллельно.
4. Приоритеты: приоритет 1 сдвигает менее важные заказы (автоматический пересчёт).
5. По каждому изделию — время изготовления и отображение на **календаре производственного процесса**; на одном экране видеть день и все циклы внутри него.
6. Перетаскивание заказов как в канбане Bitrix24.
7. (X40) Коэффициент производительности сейчас проставляется вручную, позже — **расчётный по фактической статистике** участков. Значит нужен учёт факта выполнения с первого релиза, иначе статистики не будет.
8. Разделение «нераспределено / выдано в работу» — понятие **выдачи задания на участок** (WIP).

## 3. Стек (сервер Debian 12, удалённо)

Критерии: один сервер, небольшая команда, алгоритмическая часть важнее «веб-магии», простое сопровождение, всё open-source без платных лицензий.

### 3.1. Backend
- **Python 3.12 + FastAPI** — REST + WebSocket, автогенерация OpenAPI, типизация Pydantic v2.
- **SQLAlchemy 2.x + Alembic** — ORM и миграции.
- **Движок планирования — отдельный чистый Python-пакет** (`scheduler/`) без зависимостей от БД: детерминированный, покрыт golden-тестами по Excel-примеру. Позже подключается **OR-Tools CP-SAT** для оптимизации.
- Фоновые задачи: `APScheduler` (ночной пересчёт, напоминания). Очередь (Redis + `arq`) — только когда появится реальная необходимость.
- Файлы документов: на диске сервера в volume `attachments/` (структура `order/item/category/`), метаданные в PostgreSQL, отдача через API с проверкой прав. Форматы по ответу 22: Word, PDF, DXF/DWG, Excel (+ изображения), 2–10 файлов на изделие, лимит 50 МБ/файл. PDF и картинки открываются в браузере, DWG/DXF/Word/Excel — скачиванием (просмотрщик DXF в браузере — backlog). MinIO/S3 — только если появится вторая площадка. Бэкап volume идёт тем же `restic`.
- `openpyxl` — экспорт Excel (импорт — backlog). `aiogram` — уведомления (фаза 5).
- Тесты: `pytest`, `hypothesis` (свойства планировщика: нет пересечений мощности, зависимостей не нарушает).

Альтернатива: TypeScript/NestJS единым языком с фронтом. Не рекомендую: расчётная часть и OR-Tools удобнее на Python, а у команды уже есть Python-инструменты.

### 3.2. Frontend
- **React 18 + TypeScript + Vite**, одна PWA с адаптивной вёрсткой: планировщик работает на ПК, рабочие — на телефоне или ПК (ответ 20). Терминал проектируется mobile-first, Монитор — desktop-first.
- UI-кит: **Mantine** (таблицы, формы, даты, dropzone для файлов, тёмная/светлая тема, RU-локаль из коробки) — или shadcn/ui + Tailwind.
- **TanStack Query** (данные), **TanStack Table** (списки), **react-hook-form + zod** (формы).
- **dnd-kit** — drag-and-drop в канбане и на таймлайне.
- Таймлайн/Гант — **собственный компонент на SVG/Canvas** (ядро продукта, коммерческие Bryntum/DHTMLX не нужны; `vis-timeline` как быстрый старт для прототипа).
- Графики: **ECharts** (тепловые карты загрузки, план/факт).
- Реалтайм: WebSocket с сервера → инвалидация запросов.

### 3.3. Данные и инфраструктура
- **PostgreSQL 16** — единственная БД (заказы, план, факт, аудит). JSONB для гибких параметров участков.
- **Docker Compose**: `postgres` + `api`. Статику собирает Node и отдаёт **nginx хоста на :8083** (как Fasad на :8082). `systemd` юнит на compose. **Не ставим Caddy на :80/:443** — на этом сервере `:80` занят Plitka, `:8081` KitchenSimples, `:8082` Fasad_Monzana.
- **HTTPS в MVP отложен**: Let's Encrypt HTTP-01 требует `:80`. Пока публичный URL — `http://109.248.163.211:8083/`. После покупки домена — сертификат через DNS-01 или отдельный `:443`, не отбирая `:80` у Plitka.
- **Публичный IP:** не открывать Postgres и API наружу (только `127.0.0.1:5433` и `127.0.0.1:8790`); наружу — nginx `:8083`. SSH по ключам, `fail2ban`, лимит логина, `argon2`. Порт `:8083` открыть в firewall отдельно.
- Бэкапы: `pg_dump` ежедневно + копия на Synology / S3-совместимое хранилище (`restic`). Проверка восстановления раз в месяц.
- Мониторинг: **Uptime Kuma** (доступность) + логи Docker → `journald`; ошибки — **GlitchTip** (self-hosted Sentry-совместимый) — опционально.
- CI/CD: GitHub Actions → тесты → сборка образов → деплой по SSH (`docker compose pull && up -d`). Окружения: `staging` и `prod` на одном сервере через разные compose-проекты/порты.
- Доступ: SSH по ключам, `ufw` (22, 80, 443), `fail2ban`, обновления `unattended-upgrades`.
- Аутентификация: JWT (access + refresh), роли **admin / планировщик / конструктор / снабженец / рабочий участка / наблюдатель**; у каждого из 10–20 пользователей персональная учётка (отметки «взял / готово» именные). Пароли `argon2`; на телефоне — долгоживущая сессия с PIN.

Сервер заказчика (ответы 25–26): 2 ядра, 8 GB RAM, диск 500 GB, Debian 13, публичный IP, SSH, администрирует заказчик — для нагрузки 10–20 пользователей достаточно с запасом; staging и prod размещаются на нём же. Место под документы: при 2–10 файлах на изделие ориентир 10–30 GB в год, 500 GB хватает на годы вперёд без архивации; локальная копия последних бэкапов (~20 GB) тоже помещается, основная копия — вне сервера.

## 4. Архитектура

Модульный монолит (один сервис, чёткие границы модулей — микросервисы здесь избыточны):

```
web (React PWA)  ──HTTP/WS──►  api (FastAPI)
                                 ├── auth        пользователи, роли, аудит
                                 ├── catalog     виды изделий, участки, маршруты (DAG), специальности
                                 ├── orders      заказы, изделия, форма ввода, документы (производство / закупка)
                                 ├── calendar    рабочие дни, смены, явка сотрудников
                                 ├── scheduler   чистый движок: план по изделиям и участкам
                                 ├── execution   выдача в работу, факт (старт/готово/объём), терминал
                                 ├── analytics   загрузка, план/факт, расчёт коэффициентов
                                 └── notify      Telegram / e-mail
                                 └── PostgreSQL
```

### 4.1. Модель данных (ядро)

- `customer`, `order` (номер, заказчик, дата договора, дата запуска, **приоритет заказа**, `claimed_by` — конструктор, взявший заказ, статус)
- `order_item` (изделие: вид, кол-во, **приоритет изделия**, м², коэф. конструктора, статус, маршрут)
- `attachment` (изделие, категория `production` | `procurement`, файл, размер, кто и когда загрузил) — наличие `procurement` включает шаг Комплектации для изделия
- `product_type` (вид изделия, коэф. конструктора по умолчанию, маршрут по умолчанию)
- `work_center` (участок: название, единица, мощность как «X единиц за N рабочих дней», нормативный вес, порядок, активен, `is_gate` для Комплектации, `wip_limit_per_worker` для конструкторов)
- `route`, `route_step` (участок, предшественники — DAG, метрика загрузки: м² / м.пог / изд. / заказ, `skipped_for_product_types` — на будущее)
- `employee`, `specialty` (роль, вес), `attendance` (дата, сотрудник, присутствие/вес)
- `production_calendar` (рабочие дни, смены, праздники)
- `schedule_slot` (изделие × участок: план. старт/финиш, объём, `pinned`, версия плана)
- `work_event` (факт: участок, изделие, `taken` / `done` / `materials_confirmed`, объём, кто, когда) — из него выводятся статусы «нераспределено / выдано / готово» и статистика для X40
- `audit_log`

### 4.2. Алгоритм планирования v1 (эвристика с конечной мощностью)

1. Отсортировать изделия: **приоритет заказа → приоритет изделия → дата запуска → дата договора** (ответ 19).
2. Для каждого изделия пройти маршрут в топологическом порядке (в v1 — линейная цепочка §1.2).
3. Для шага: `ранний_старт = max(финиш всех предшественников, доступность участка)`; мощность на день = `(X / N) × коэф_производительности(день)` из явки; списывать объём по **рабочим дням календаря 5/2** с переносом остатка; получить старт/финиш.
4. **Конструирование** — пул конструкторов, единица работы — **заказ целиком** (ответ 18): план назначает заказ тому конструктору, который освободится раньше, длительность = число изделий заказа / ((X / N) × КПД_конструктора). Фактическое назначение — когда конструктор нажал «Взять»; заказ исчезает из очереди остальных. Изделия заказа завершаются по одному (с приложенными документами) и по одному уходят дальше, не дожидаясь всего заказа.
5. **Комплектация — условный шлюз по изделию** (ответы 17, 21, 23): шаг включается, если конструктор при завершении изделия выбрал «Закупка нужна»; последующие шаги не стартуют раньше события «всё в наличии» по этому изделию. При «не нужна» изделие идёт сразу на Пилу. Нагрузка на Комплектацию считается по заказам — 4 заказа в день (ответ 24): все изделия одного заказа занимают один слот. До завершения конструирования план считает Комплектацию включённой (консервативная оценка), после — по факту.
6. **Уже начатые шаги не вытесняются** и не сдвигаются: смена приоритета влияет только на незапущенные шаги.
7. Закреплённые вручную блоки (`pinned`) — жёсткие ограничения, остальные планируются вокруг.
8. Изменение приоритета / мощности / явки / факта → пересчёт незакреплённого и незапущенного, пользователю показывается diff перед применением.
9. Результат — версия плана; старые версии хранятся (история, откат).

Статусы изделия и участка не вводятся руками, а вычисляются из `work_event`: **нераспределено** — ни один шаг не начат; **выдано / в работе** — есть `taken` без `done`; **готово** — `done` на последнем шаге. Оптимизатор (CP-SAT) — отдельный этап после того, как эвристика принята производством.

## 5. Дизайн (приблизительный)

Принципы: одна главная панель «Монитор» отвечает на вопрос «что делается сегодня и что горит»; действие — перетаскиванием; каждая дата объяснима; одна PWA для ПК и телефона — экраны планировщика desktop-first, экраны исполнителей mobile-first (ответ 20); русский язык; светлая тема по умолчанию (цех), тёмная — опция.

### Экраны

0. **Форма заказа** (ввод — единственный источник данных в MVP). Шапка: заказчик (справочник с автодополнением), номер договора, дата договора, дата запуска, приоритет заказа. Таблица изделий прямо в форме: вид, количество, м² (м.пог считается), приоритет изделия, комментарий; добавление строки Enter'ом, дублирование строки, итоги по м² внизу. КПД конструктора задаётся в карточке сотрудника, не в позиции. Сохранение — черновик или «в очередь конструкторов».
1. **Монитор** (главный). Слева — участки строками (swimlanes), сверху — дни. Блоки — изделия на участке, цвет = заказ, штрих = просрочка, процент = загрузка участка за день. Маркер «сегодня». Переключатель День / Неделя / Месяц. Клик по дню — панель «день»: все участки, что в работе, кто присутствует, что ждёт. Правая панель по клику на блок: заказ, изделие, объём, почему такая дата, кнопки «закрепить / сдвинуть / приоритет».
2. **Канбан.** Колонки — статусы (не распределено → в работе на участке → готово) либо участки. Карточки — изделия. Статус меняется автоматически по событиям «взял / готово» (ответ 6); перетаскивание = порядок в очереди участка и приоритет → пересчёт с предпросмотром.
3. **Заказы.** Таблица с фильтрами и статусами, карточка заказа с изделиями и документами, массовая смена приоритета; импорт из Excel — backlog.
4. **Участки и маршруты.** Список участков (добавить, перетащить порядок, мощность, единица, нормативный вес). Визуальный редактор маршрута по виду изделия (узлы-участки, связи-зависимости, параллельные ветки).
5. **Персонал и явка.** Сотрудники и веса; сетка «день × сотрудник» с отметками присутствия → мощность участка на день пересчитывается автоматически.
6. **Календарь производства.** Рабочие/нерабочие дни, смены, праздники.
7. **Рабочее место конструктора** (в MVP, ПК и телефон). Две вкладки: «Доступные заказы» (общая очередь, кнопка «Взять» — заказ исчезает у остальных) и «Мой заказ» (пока не завершён, «Взять» следующий недоступен). Внутри заказа — изделия; у каждого две зоны загрузки документов: **Производство** (чертежи, схемы, дизайн) и **Закупка** (материалы, фурнитура). Кнопка «Изделие готово» активна при наличии хотя бы производственных документов и требует выбора «Закупка нужна / не нужна» (ответ 23); при «нужна» изделие уходит в Комплектацию (если файлов в «Закупке» нет — предупреждение), при «не нужна» — сразу на Пилу.
8. **Терминал участка** (в MVP, телефон и ПК, каждый рабочий под своей учёткой). Очередь участка крупными карточками с доступом к производственным документам изделия: «Взять», «Готово», ввод объёма. У Комплектации — список изделий с документами на закупку и кнопка «Всё в наличии» по каждому изделию. QR с маршрутного листа — фаза 5. Минимум текста, максимум контраста, работает одной рукой на телефоне.
9. **Аналитика.** Загрузка участков (тепловая карта), план/факт по участкам, доля в срок, предлагаемые коэффициенты производительности (X40) с кнопкой «применить».
10. **Настройки.** Пользователи, роли, уведомления, интеграции.

Макеты экранов «Монитор», «Канбан» и DAG маршрута — в канвасе `monza-production-plan.canvas.tsx` рядом с чатом; финальные макеты — в Figma на фазе 0.
